Scope and current status

personal-health is a personal project maintained by michael-bill for accessing the account owner's Fitbit data through the Google Health API. This public website documents the project. The repository provides an early version of a Python MCP server for private use by the operator and personally known users. Each user authorizes access to their own account. The public website does not run the server.

This public website

This website contains static information pages. It does not request Google authorization, read health records, accept credentials, or use application analytics, advertising scripts or application cookies. It is hosted by GitHub Pages. GitHub processes hosting information, including visitors' IP addresses, as described in the GitHub Privacy Statement.

Google data requested by the connection

Only the categories explicitly authorized by the account owner may be accessed:

  • Activity, fitness and workout records.
  • Health metrics and measurements, such as available heart rate and related measurements.
  • Sleep records.
  • Profile information, including age when available.
  • Account settings, such as time zone and preferred measurement units.
  • Nutrition and hydration logs.
  • GPS locations recorded during exercise.

The connection requests read-only Google Health permissions. It does not request access to Gmail, Drive, contacts or other unrelated Google services.

Purpose and sharing

Health data is used to retrieve the owner's records and support the owner's personal review and requested analysis. This project does not sell that data or use it for advertising. Its use of information received from Google APIs must adhere to the Google API Services User Data Policy, including the Limited Use requirements, and the applicable Google Health API policies.

If the owner connects an MCP client or AI assistant, the records requested through that connection may be transmitted to that client and its configured model provider. That provider's data handling and retention settings apply. The owner must choose and configure these services before sharing health data. The project is not intended to use Google user data to train general-purpose AI models.

Storage and credentials

The software runs on a private computer or self-hosted server. Two connection modes are supported. In forwarded mode clients send their Google credentials on each request and the server does not persist those credentials. In OAuth mode users connect through browser consent; Google refresh tokens and registered OAuth client secrets are stored encrypted in SQLite, with the encryption key kept separately on the server. MCP access and refresh tokens are independent from Google tokens; only their hashes are stored. Short-lived Google access tokens are cached in process memory. The server process and its administrator can access credentials while processing requests. HTTPS is required outside loopback. The OAuth login uses temporary, secure browser cookies for consent and callback protection; these cookies are on the server origin, not this static website. SQLite may store health response caches, query continuations, hashed account bindings and MCP key hashes. Requested JSONL and TCX exports are private server files. These health files are not encrypted at rest by the application; the operator is responsible for disk encryption and private backups. Credentials and health records must remain outside Git and this website.

Operational usage statistics

The MCP records invocation time, an opaque user identifier, tool name, outcome, duration, fixed error code, upstream request counts, cache hits and returned-record counts in SQLite and structured server logs. It does not log tool arguments, health values, request date ranges, IP addresses or credentials. Tool names can reveal which category was requested. Global usage reports are available to the installation operator, not other MCP users. This logging applies to the MCP installation, not this static website.

Retention, deletion and revocation

The default response cache is valid for five minutes and query cursors for 24 hours. Expired entries and usage events older than 90 days are deleted on server startup or when the operator runs the prune command; the systemd deployment includes a daily pruning timer. OAuth login transactions expire after ten minutes; authorization codes after two minutes; MCP access tokens after fifteen minutes; rotating MCP refresh tokens after thirty days from issuance. Encrypted Google connections remain until disconnected or removed by the operator. Export files remain until the operator removes them. The operator controls log rotation and backup retention. Users of a shared installation should contact its operator to delete stored copies. Cache expiry is not secure disk erasure.

The owner controls retention on their installation and can delete locally stored records and credentials. Access to Google data can be revoked at Google Account connections. Revocation stops further authorized API access; it does not delete previously exported records or copies already sent to a separately configured provider. Those copies must be deleted from the relevant installation or service.

Contact and changes

Questions about this project can be raised through GitHub issues. Public issues must not contain health information or credentials. Policy changes will be published on this page with an updated date.
